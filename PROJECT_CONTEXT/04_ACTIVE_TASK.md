**Sprint 4.3 — Evidence-Based Response Engine**: Replaced mock answer generation with real evidence-based reasoning. Delta no longer answers from `lib/delta-mock-responses.ts` (deleted) — every answer now traces back to an actual `Relationship`. Three new generic, relationship-driven modules in `lib/intelligence-engine/`, all following the established interface + implementation class + exported singleton pattern:

- `EvidenceEngine` (`evidence-engine.ts`) — `collect({text, entities, scopes, relationshipType?}): Promise<Evidence[]>`. For graph-native intents (Evidence/Impact/Related Knowledge), preserves the existing narrower-tier-first cascade from Sprint 4.2, now spanning three tiers: current discussion node → its linked knowledge objects (via the existing `getKnowledgeObjects` server action) → whole project. For every other intent (location/status/material/dimension/...), gathers all three tiers unconditionally and matches candidates by requiring every extracted entity to match somewhere on the candidate (an AND, not an OR — this is what makes a compound question like "is the staircase at the entrance" correctly return nothing when only one of the two things is actually in the graph). A real bug was caught and fixed mid-implementation: matching originally checked both sides of a relationship unconditionally, so a discussion literally named "Entrance Accessibility" trivially matched every one of its own unrelated evidence items on any "entrance" query, since the *discussion's own label* satisfied the term rather than the actual evidence. Fixed by excluding the caller's own reference node from consideration (`candidateSides()`) — verified via a temporary, since-removed smoke-test route against the real seed data before and after the fix.
- `ConfidenceScorer` (`confidence-scorer.ts`) — deterministic High/Medium/Low/None, derived purely from `Evidence.confidence` (already tier-weighted: node=1.0, linked-knowledge-object=0.75, project=0.5, × relevance) — no separate tier field needed. High needs ≥2 direct-evidence items in current context; Medium is 1 such item or any indirect (impact/related) item in current context; Low is project-only or weak; None is empty.
- `ReasoningEngine` (`reasoning-engine.ts`) — `explain(entities, evidence, confidence, currentContextType?): ReasoningResult`. States only that a relationship exists and its type — never a fabricated semantic claim (e.g. never "confirms the width is 4 feet"). Lists absent evidence types (excluding the current context's own type) as "missing," and a fixed conclusion string keyed by confidence.

`delta-query-resolver.ts` was rewritten (not moved again) to run Evidence → Confidence → Reasoning after `intelligenceEngine.process()`, then shape the result using `ResponsePlan.layout` (computed since Sprint 4.2, genuinely used for the first time): `related_list` → a related-knowledge listing, `comparison` → a two-subject comparison (degrading honestly to an "unknown" result when fewer than two entities independently produce distinct evidence), `short_answer` → a real Answer when confidence is High/Medium, or an honest "I couldn't determine an answer" Unknown when Low/None. `revision`-layout and workflow-routed queries return a plain, explicit "not available"/"not a question" message rather than being forced through evidence collection. `DeltaResponsePanel.tsx` gained shared `ConfidenceBadge`/`EvidenceList`/`ReasoningSection` components and new `comparison`/`unknown` rendering branches; the old fabricated "Approved By" pills are gone since that data no longer exists.

Verified against real seed data (project `3c2384a0-bc60-4116-ba8c-5f1f52eedb42`) via a temporary, unauthenticated smoke-test API route (added and removed within this session): a real evidence listing at High confidence, a genuine non-mock Answer at Medium confidence (`"Weather-protected clearance to accessible entrance"`, a real Requirement's own label), Sprint 4.1's existing ambiguity clarification still firing correctly ahead of evidence collection, and a genuinely unsupported query ("Where is the toilet?") producing an honest Unknown result with zero fabricated content.

Not built this sprint: revision comparison, real semantic/embeddings-based matching (current matching is literal string/whole-word), any actual Requirement/Decision/Issue/Action workflow execution (Orchestrator's workflow routing remains advisory-only). High confidence is unreachable for generic intents given the current entity dictionary vs. relationship-label overlap — a data limitation, not a scorer defect.

This sprint added the three modules that didn't exist yet, all in new `lib/intelligence-engine/`, all following the same interface + implementation class + exported default singleton pattern as Module 1:

- `ContextEngine` (`context-engine.ts`) — Module 2. `resolveScopes()` turns the Comprehension Engine's resolved context into an ORDERED list of concrete scopes to search, narrowest first: a `node` scope (discussion, if present) before a `project` scope. Only `discussionId` becomes a node scope — `knowledgeObjectId`'s node type can't be known without an extra repository lookup this sprint doesn't add, and `page` has no equivalent in `RelationshipQuery` at all, so both stay metadata-only (same limitation Sprint 4.1 already documented for `knowledgeObjectId`).
- `Orchestrator` (`orchestrator.ts`) — Module 3. `route(intent, destination)` decides what should happen next; it never performs the work. Two-tier: graph-native intents (Evidence/Impact/Related Knowledge) always route to `knowledge_graph_query` regardless of destination; everything else routes via an exhaustive, TypeScript-checked `DeltaDestination → RoutingTarget` table (`RoutingTarget` has 8 values total, matching the brief's named destinations; `upload_pipeline`/`comparison_engine` are unreachable this sprint by design).
- `ResponsePlanner` (`response-planner.ts`) — Module 4. `plan(intent)` decides how an answer should be presented (not what it is) via an exhaustive, TypeScript-checked `DeltaIntent → ResponsePlan` table across four families: single-fact Q&A → short answer; graph-native listing → related list; comparison/conflict → comparison layout; revision → changes/affected-knowledge/related-drawings layout.
- `IntelligenceEngine` (`intelligence-engine.ts`) — the top-level class, constructor-injected with all four modules (comprehension service + the three new ones, all defaulting to singletons). `.process()` assembles the canonical `IntelligenceEngineResult` (`types/intelligence-engine.ts`): original/normalized message, language, intent, entities, context, context scopes, destination, per-stage + overall confidence, routing decision, response plan, and an advisory `suggestedNextAction` (`requiresApproval` always `true` — "AI proposes, user approves" encoded as data).

`delta-query-resolver.ts` **moved** from `lib/comprehension/` to `lib/intelligence-engine/` (the only caller, `useDeltaPanel.ts`, needed a one-line import path change — same function name/signature/behavior contract). It now calls `intelligenceEngine.process()` instead of `deltaComprehensionService.comprehend()` directly, and for `knowledge_graph_query` routing, genuinely searches the current context first: the existing node-scoped query (`getEvidenceForNode`/`getImpactsForNode`/`queryRelationships({node,...})`, unchanged) runs first, and only on an empty result does a new project-wide fallback run — `queryRelationships({projectId, relationshipType})`, filtered per intent so it never mixes Evidence with Impact/Related results. This is the first sprint where "search current context first, then expand to project" is real, verified behavior (confirmed against `MockRelationshipRepository`'s actual matching logic) rather than an unimplemented aspiration. Every other routing target, and any empty graph result even after the project-wide fallback, still falls back to the unchanged `lookupDeltaMock`, fed the translated text exactly as Sprint 4.1 built it.

Not built this sprint (explicitly out of scope, matching the brief): embeddings, semantic search, graph reasoning, LLM prompting, OCR, upload intelligence, revision comparison. `ResponsePlan` is computed but does not yet drive `DeltaResponsePanel`'s actual rendering — same "compute now, surface later" posture Sprint 4.1 took with Destination Prediction. No workflow actually creates a Requirement/Decision/Issue/Action as a result of Orchestrator routing — those targets are advisory metadata only.

**Sprint 4.1 — Delta Comprehension Engine (DCE)**: Built the first stage of every Delta interaction, ahead of the Knowledge Graph: User → Comprehension → Knowledge Graph → Reasoning → Answer. `DeltaComprehensionService` (`lib/comprehension/delta-comprehension-service.ts`) orchestrates six independently-replaceable modules, each following interface + implementation class + exported default singleton, injected into the orchestrator via constructor parameters (not hardcoded imports) — this is the one deliberate deviation from the Sprint 4.0 repository pattern, made specifically so a future LLM-backed module can replace any single stage without touching the orchestrator or any other module:

- `NormalizationService` (`normalization-service.ts`) — dictionary-driven spelling/abbreviation/synonym normalization (staircse/staircas/stair case/stairs → staircase; Fire Door/FR Door → Fire Rated Door; CL → Client; PMC → Project Management Consultant; WC/Washroom → Toilet).
- `LanguageService` (`language-service.ts`) — English/Hindi/Hinglish detection plus internal-only translation via structural sentence rules (Hindi is SOV, English is SVO, so this can't be a plain word dictionary): "staircase kahan hai?" → "Where is the staircase?", "fire exit ka kya hua?" → "What is the status of the fire exit?", "client ne marble bola tha?" → "Did the client request marble?".
- `IntentClassifier` (`intent-classifier.ts`) — 17 intents (Location/Status/Approval/Reason/Dimension/Material/Requirement/Decision/Action/Issue/Risk/Conflict/Evidence/Impact/Comparison/Revision/Related Knowledge) via ordered regex rules, where rule order encodes priority.
- `EntityExtractor` (`entity-extractor.ts`) — dictionary-driven (`{ term, type }`, `type` an open string, not a closed enum), including an ambiguity mechanic (a shorter term contained in a longer dictionary term, e.g. "staircase" inside "fire staircase", surfaces both as low-confidence `alternatives`).
- `ContextResolver` (`context-resolver.ts`) — carries through whatever page/discussion/knowledge-object/project context the caller supplies; the actual "where is the user" wiring lives in the calling React components, which already know their own IDs.
- `DestinationPredictor` (`destination-predictor.ts`) — Delta Query / New Discussion / New Requirement / New Decision / New Issue / New Action, question-detection first, then ordered statement rules, falling back to New Discussion (today's existing default) when nothing matches.

Every stage returns a 0–1 confidence; `DeltaComprehensionService` takes the minimum across intent/entities/destination and returns a clarifying question (not a guess) below 0.5 (`CONFIDENCE_THRESHOLD`).

`delta-query-resolver.ts` (originally in `lib/comprehension/`, moved to `lib/intelligence-engine/` in Sprint 4.2) is the concrete integration point: `useDeltaPanel` (the "Ask Delta" hook, used by `DiscussionPrompt` and `ReplyBar`) now calls `resolveDeltaQuery()`, which runs comprehension first, then — only for Evidence/Impact/Related Knowledge intents with a discussion resolved in context — queries the real `RelationshipRepository` (Sprint 4.0) via its existing actions. Every other query, and any query without discussion context, falls back to the pre-existing `lookupDeltaMock`, now fed normalized/translated text rather than the raw string, which is why every Ask-Delta query — not only the ones that touch the graph — genuinely passes through the Comprehension Engine first.

UI changes were deliberately minimal (this sprint is architecture, not a redesign): one new "clarification" rendering branch in `DeltaResponsePanel`, and one small non-blocking destination-prediction badge in `DiscussionPrompt` (e.g. "→ Requirement") that appears as the user types — at the time, pressing Enter/Send still created a Discussion/reply regardless of the hint; the prediction was a hint only, never an override (this is the exact gap Sprint 4.3.1 later closed for the Journal's own Enter/Send action). `ReplyBar`, `DiscussionMessages`, `DiscussionDetail`, `DiscussionCard`, and `Workspace` all gained an optional `context` prop threaded down from wherever `discussionId`/`projectId` is already known.

Not built this sprint (explicitly out of scope, per the brief): embeddings, semantic search, graph reasoning, LLM prompting, OCR, upload intelligence, revision comparison. `knowledgeObjectId` context is implemented in the types/resolver but currently unused — no Ask-Delta entry point exists yet on the Knowledge Object Detail page.
