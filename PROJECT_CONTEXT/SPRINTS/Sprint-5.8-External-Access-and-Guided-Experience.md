# Objective

Not new intelligence — making Delta usable by real architectural firms and real clients. A Lead Architect should be able to create a project, invite a real client, and walk through Agreement → Project Setup naturally, without exposing implementation details (invite codes, raw URLs, internal ids, lifecycle stage strings) and without ever wondering "what do I do next?"

---

# Background

Sprint 5.7 built the Governance Engine and the Agreement → Setup → Review → Activation lifecycle itself. This sprint is the presentation and access layer on top of it: the invitation flow still worked but leaked implementation details, invite links were built from `window.location.origin` rather than a configured base URL, the Agreement page read as a form rather than a status board, uploads had no consistent feedback, the workflow order wasn't actually enforced past the UI's own happy path, the DIGA→Delta rename was incomplete, auth pages used a completely different (hardcoded slate/cyan) visual language than the rest of the app, `/firm` had no navigation shell at all, and there was no visible way to sign out.

---

# Scope

## Module 1 — External Application URL
`lib/invitations/share-links.ts` now builds every invitation link from `process.env.NEXT_PUBLIC_APP_URL` (already defined in `.env.local`, already used once before by `auth-actions.ts`'s password-reset redirect) instead of `window.location.origin`. Falls back to `window.location.origin` only if the env var is genuinely unset, so a misconfigured environment degrades rather than breaks. No other hardcoded `localhost` references existed anywhere in the app source (confirmed by a full-repo grep before starting).

## Module 2 — Invitation Experience
`project_invitations` gained `invitee_name` (new migration). The Agreement page's Invite Main Client form now collects Name / WhatsApp Number (required) / Email (optional) instead of an either-or email-or-phone pair. `InviteShareSheet.tsx` was rewritten to show exactly two actions — **Copy Invitation Link** and **Share on WhatsApp** — and never renders the invite code or raw URL on screen (Copy Link copies it silently to the clipboard). WhatsApp now deep-links straight to the invitee's own number (`https://wa.me/<digits>?text=...`) instead of the generic compose screen. SMS/Email links are still generated by `buildInviteShareLinks()` for architecture-compatibility with a future provider — just not surfaced as buttons, matching the brief's own explicit two-button list.

## Module 3 — Agreement Status Experience
`AgreementWorkspace.tsx` gained a `StatusBoard` shown at all times: Agreement Uploaded, Main Client, Invitation Status, Agreement Status, Discussion Status, Current Version, and a computed **Waiting For / Next Action** line (`describeStatus()`) — one pure function over the same real data the page already has (agreement, roster, invitations, discussions), never a second status system. Never shows `lifecycle_stage` raw values or invite codes.

## Module 4 — Upload Experience
`components/shared/useUploadAction.ts` (a reusable idle/uploading/success/error state machine, duplicate-submit-proof by construction) and `components/shared/UploadStatusLine.tsx` (the shared success/failure line) — wired into the Agreement's initial upload, the Agreement revision upload, and the Import Workspace's per-category upload (which previously hand-rolled its own uploading/error state with no success confirmation at all). No byte-level progress exists anywhere in this codebase (Server Actions have no progress-event API) — "show progress" is an honest indeterminate uploading state, never a fabricated percentage.

## Module 5 — Workflow Order
`requireAgreementAccepted()` (new, `lib/governance/activation-gate.ts`) redirects `/setup` and `/setup/review` back to `/agreement` whenever `lifecycle_stage` is still `draft`/`agreement_review` — neither page had any guard of its own before this sprint, reachable by direct URL regardless of Agreement status. The Sidebar's pre-Active nav no longer offers "Project Setup" as a destination until the Agreement is actually accepted.

## Module 6 — Brand Migration
3 remaining user-facing "DIGA" occurrences fixed (`/auth`'s "Welcome to DIGA", the Import page's description, the invitation share message). Internal engineering comments and the doc filename `DIGA-CORE-ARCHITECTURE-V2.md` were left unchanged, per the brief's own "internal identifiers may remain unchanged" allowance — they're not user-facing.

## Module 7 — Unified Design System
New `components/auth/AuthShell.tsx` (`surface-primary`/`surface-secondary`/`border-subtle`/`accent-primary` — the same tokens every internal page already uses, plus the same `rounded-xl` input / `rounded-full` button shapes `AgreementWorkspace.tsx` established) replaces the hardcoded `bg-slate-950`/`bg-cyan-500` palette across all 6 auth-adjacent pages: `/auth`, `/auth/register`, `/auth/forgot-password`, `/auth/reset-password`, `/auth/verify`, `/logout`. `/invite/[code]` already used real tokens (built that way from the start in Sprint 5.7) and needed no change.

## Module 8 — Guided Workflow
The same "Waiting For / Next Action" pattern Module 3 established now also appears on the Project Setup checklist (computed from the real checklist state — "Next: Invite Consultants." / "Ready for Delta Project Review.") and the Delta Project Review panel ("Ready to Activate Project." once confirmed).

## Module 9 — Navigation Polish
`AppShell.tsx`'s children slot gained `overflow-y-auto` — the single point every workspace page now scrolls independently through, rather than each page needing its own (only `knowledge-bank/page.tsx` had opted in before; that now-redundant declaration was removed). Sidebar items reordered: project-scoped items now lead, Firm/All Projects follow, when inside a project — previously Firm/All Projects always sat first regardless. `/firm` gained a layout (`app/firm/layout.tsx`, mirroring `app/projects/layout.tsx` exactly) — it had **no navigation shell at all** before this sprint, a genuine dead end reachable from the Sidebar's own "Firm" item.

## Module 10 — Sign Out
`components/delta/AccountMenu.tsx` replaces the TopBar's hardcoded, non-interactive "MC" avatar button with a real dropdown: signed-in person's name/email (reusing `getFirmContext()`, already exported, no new query), honest "Soon" stubs for Profile/Account, and a real Sign Out linking to the pre-existing, unmodified `/logout` route. Built as a flat menu-item list specifically so Switch Firm/Switch Project/Settings can be appended later without restructuring.

# Implementation Notes (Architecture Decisions)

- **`useUploadAction` is intentionally honest about what "progress" means**: no XHR/byte-level progress event exists anywhere in this codebase's upload path (Server Actions have no such API), so every upload button shows an indeterminate "Uploading..." state, never a fabricated percentage.
- **The WhatsApp share link now targets the invitee's own number** (`https://wa.me/<digits>?text=...`) rather than the generic `https://wa.me/?text=...` compose screen, since Module 2 made the number a required field collected before the invitation exists — a direct consequence of that requirement, not a separate decision.
- **`invitee_name` is a genuinely new column, not new business state** — it exists purely to let the share message and the `/invite/[code]` landing page greet someone by name; it's never validated against the person's eventual real name and the flow works identically if it's left blank.
- **The Sidebar reorder and the `/setup` gating share one boolean** (`agreementAccepted`, derived from `identity.lifecycleStage`) computed once in `AppSidebar.tsx` — Module 5 (don't offer Setup as a destination) and Module 9 (navigation consistency) turned out to be the same underlying fact, not two separate mechanisms.
- **`/firm` having no layout at all was found during the Module 9 audit, not assumed** — a full grep for `AppShell` usage showed only `app/projects/layout.tsx` mounting it; `/firm` rendered as a bare page under the root layout with zero sidebar/topbar, meaning the Sidebar's own "Firm" nav item led to a real dead end. Fixed with one new file, mirroring the existing layout exactly — no changes to `firm/page.tsx` itself were needed since none of its content assumed full-viewport rendering.
- **`AppShell`'s scroll fix is a single-point change** (`overflow-y-auto` on the one children slot every page renders into) rather than touching every page individually — Dashboard, Journal, Timeline, Participants, and Import previously had no scroll container of their own at all; only `knowledge-bank` had opted in, and that now-redundant declaration was removed to avoid a nested scroll container.

# Completion Notes

Completed work: see Files Expected to Change above — a Lead Architect can now create a Firm, create a Project, upload an Agreement, invite a Main Client by name and WhatsApp number, and hand them a real, environment-correct link, with the whole surface (auth pages through the Agreement/Setup workflow) reading as one consistent product rather than a collection of features bolted together.

Known limitations (honestly disclosed, not fabricated away):

- No real WhatsApp Business API integration — "Share on WhatsApp" opens a `wa.me` deep link in the user's own WhatsApp client, per the brief's own explicit "do not implement yet" instruction. `buildInviteShareLinks()` is the one seam a future provider would replace.
- No byte-level upload progress — every upload shows an honest indeterminate state, not a percentage, since no such signal exists in this codebase's Server-Action-based upload path.
- Profile and Account menu items are real, visible, honest "Soon" stubs — no profile-editing or account-settings functionality was built this sprint.
- One unrelated Storage blob (not created by this session) remains in the shared bucket, left alone rather than deleted without certainty of its origin — consistent with every prior sprint's own "only clean up what you created" discipline.

Future extension points:

- `AccountMenu`'s flat menu-item structure was built specifically so Switch Firm, Switch Project, and Settings can be appended without restructuring, once those features exist.
- `useUploadAction`/`UploadStatusLine` are already generic — a future Drawings/BOQ/Specifications/Reports upload entry point outside the Import Workspace would reuse them directly, not reimplement upload state.
- `DOCUMENT_CHANGE_ANALYZERS` (Sprint 5.7) and this sprint's status-board pattern compose naturally — a future content-diffing analyzer for BOQ/Specification/Report would show up on the Agreement-style status board with no new UI work.
